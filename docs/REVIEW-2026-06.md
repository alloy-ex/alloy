# Alloy 0.12.2 — Critical review (June 11, 2026)

Scope: toolchain update to Elixir 1.20.1/OTP 28, warning fixes, architecture
review, and an ecosystem comparison against current Hex packages.

## 2. Premise: does it have a place?

Mostly yes, but the window is narrowing fast.

The thesis (BEAM/OTP is the natural agent runtime) was validated loudly this
year — OpenAI's Symphony orchestrator reference implementation shipped in
Elixir, and Dashbit published "Why Elixir is the best language for AI." The
problem is that validation attracted a crowd: **at least seven direct or
near-direct competitors launched Dec 2025–May 2026** (sagents, condukt, nous,
agens, adk_ex, jido_ai 2.x, plus ash_ai's expansion).

Honest traction read: ~635 downloads/week real run-rate, 0 Hex dependants,
75 GitHub stars, single maintainer, no release in ~6.5 weeks — against jido
(5.1k/wk), ash_ai (4.3k/wk), sagents (2.1k/wk, brainlid's name recognition),
and req_llm (16.5k/wk, 31 dependants) all shipping within the last 2–3 weeks.
The headline ~258k all-time download figure is mirror/CI-inflated and should
not be cited as adoption.

What is still defensible: the "harness, not framework" position. Nothing else
in the ecosystem combines built-in coding tools (read/write/edit/bash),
compaction, prompt caching, `until_tool`, budget guard, the Anthropic
`memory_20250818` behaviour, and middleware HITL in a ~7.5k-line, 3-dep
package. jido is heavier and more abstract; sagents drags in LangChain;
req_llm alone gives you no loop. That counter-position is real — but only if
the package stays visibly alive and closes the table-stakes gaps below.

## 3. Architecture assessment

Strengths: protocol-first design with clean behaviours (Provider, Tool,
Memory, Middleware); runtime optional rather than mandatory; explicit crash
handling on async turns; no unbounded queues or blocking hot-path GenServer
calls found; tool layer is security-conscious (restricted bash by default,
`:allowed_paths`, symlink resolution, output capping); telemetry throughout.
The 0.12 "protocol library, runtime above" split is the right call and the
migration doc argues it well.

Concerns, in priority order:

1. **The package is in mid-refactor limbo and the README installs a 404.**
   `Alloy.Agent.Server`, `Alloy.Session` are deprecated for removal in
   0.13.0, with README and `docs/MIGRATION-alloy_agent.md` directing users to
   add `{:alloy_agent, "~> 0.1"}` — **which does not exist on hex.pm**
   (`hex.pm/api/packages/alloy_agent` → 404). Anyone following the docs today
   hits a resolver error; anyone on the deprecated modules has no migration
   target. This is the single most damaging issue in the repo: publish
   alloy_agent before any 0.13 work, or retract the deprecations. The 0.12.1
   → 0.12.2 retraction note about `AlloyAgent.Events` shows this churn is
   already confusing users.

2. **The provider-adapter treadmill is a strategic liability.** Six hand-rolled
   wire formats plus a hand-curated model catalog compete head-on with
   req_llm + llm_db (45 providers, 665+ models, cost metadata, dedicated
   team, 2026.6.0 released this week). The catalog in `model_metadata.ex` is
   already stale: newest Anthropic entry is `claude-opus-4-6` — missing
   `claude-opus-4-8` and `claude-fable-5`, both GA by June 2026 — and the
   hardcoded 200k context limits need re-verification against current model
   tiers (1M-context variants exist now). Suffix patterns and
   `model_metadata_overrides` soften this but don't solve it. Options:
   (a) accept the treadmill and automate catalog refresh from models.dev,
   (b) offer an optional `Alloy.Provider.ReqLLM` adapter so the loop rides on
   the ecosystem's provider layer while keeping native adapters for the
   zero-dep purists, or (c) shrink the catalog's promises (limits only, no
   pricing). Doing nothing means perpetual staleness.

3. **Restricted bash is a speed bump, not a sandbox.** `bash -r` blocks `cd`,
   PATH changes, and redirection, but any interpreter on PATH (`python3 -c`,
   `perl -e`) yields full capability. The pluggable `:bash_executor` is the
   right escape hatch; the docs should state plainly that real isolation
   requires supplying one (container/jail/firejail), and the README's "Tool
   safety" bullet currently oversells the default.

4. Smaller items: `Alloy.Provider.Codex` is the largest module (~660 lines)
   and the most likely to rot as the upstream protocol shifts; the events
   versioned-envelope ("v1") is good discipline but undocumented for
   consumers building their own UIs.

## 4. What's missing (gap analysis vs 2026 table stakes)

- **MCP client support** — the biggest gap. condukt, ash_ai, and langchain
  ship it; anubis_mcp (150k recent downloads) is the obvious client to
  integrate. An `Alloy.Tool` adapter that wraps MCP server tools would fit
  the design boundary cleanly (it is protocol, not application workflow).
- **Durable checkpointing / resumability** — the #1 ask in the "State of
  developing agents with Elixir" forum thread. By design it doesn't belong in
  alloy core — which is exactly why alloy_agent must actually exist, with an
  optional Ecto/Oban checkpoint adapter.
- **Structured output beyond `until_tool`** — native `response_format` /
  JSON-schema enforcement per provider (instructor_lite-style), not just
  loop-until-tool-call.
- **OTel/OpenInference semantic conventions** — telemetry events exist, but a
  documented bridge (or compat with agent_obs) is becoming expected.
- **Eval/regression story** — `Alloy.Testing` covers unit stubs; nothing for
  scoring agent behaviour across model swaps (aludel/tribunal are emerging).
- Multi-agent/sub-agent orchestration is also absent, but that's a defensible
  non-goal — document it as such rather than leaving it unstated.

## 6. Recommended order of work

1. Publish `alloy_agent` 0.1 (or retract the 0.13 deprecations) — unblocks
   everything else and removes the 404 from the README.
2. Ship 0.12.3 with this pass's Elixir 1.20/req 0.6 security updates — it's a
   credible, easy "we're alive" release.
3. MCP tool adapter (anubis_mcp behind an optional dep, same pattern as
   phoenix_pubsub).
4. Model catalog refresh + automate against models.dev, or adopt an optional
   req_llm provider adapter and let llm_db carry the catalog.
5. Checkpoint/persistence adapter in alloy_agent.
6. Honest sandboxing docs for the bash tool.
